The client-side problem

Location-led tourism and real-estate teams often receive overlapping geographic records from multiple extracts, cannot reliably re-import updated data, and need to ask repeatable proximity questions without manual GIS desktop steps.

Working architecture

OSM XML extractsPython ETL + validationPostgreSQL 16 / PostGIS 3.4PostgREST 16.5FastAPI / GeoJSONLeaflet map
  • Idempotent ingestion: source+OSM type+OSM ID unique key, conflict-aware upserts; rerunning the ETL left all 726 records unchanged.
  • Spatial database: WGS84 geometry, spatial GiST indexes, geography-based distance queries measured in meters.
  • Geospatial APIs: category catalog, bounding-box GeoJSON, nearby facilities, and 500 m / 1,500 m site-category summaries.
  • REST integration: PostgREST exposing read-only collection queries and RPC; unauthorized direct writes refused.
  • Operations: separate PostgreSQL cluster, localhost-only database/REST ports, systemd services, HTTPS gateway and a database backup.

Scope & limitations

This is a technical proof of concept, not a production deployment for a client. The data covers three overlapping extracts of central Baku only; POI absence does not prove the place is absent. Site analysis counts nearby recorded features, not pedestrian travel times, investment return, or verified tourism demand. Way geometry is represented using a representative point. No private or purchased location data was used.

Supabase note: PostgreSQL/PostGIS + PostgREST provides a Supabase-compatible data/API foundation, but this demo does not include Supabase Studio, Auth, Storage, Realtime, or an actual managed Supabase instance.
